## P0 · 本文档解决的问题

**背景**：00-07 已完成价值主张、用户画像、架构框架、v1 主线、产品形态与 MSP 定位设计，但存在 6 大**闭环缺口**——平台有 AI 能力、有治理面板、有 MSP 两层客户结构，却缺少"AI 怎么收费、MSP 怎么转售、AI 怎么被审计、Agent 怎么被管理、报告怎么交付"的完整设计。本文档一次性补齐，形成**商业化闭环**（能卖、能算、能收）与**平台治理闭环**（能管、能审、能交付）。

### 设计输入（对标依据）

- **SN 逆向文档**（itom-reverse 仓库 · 2026-08-21 调研）：
  - 计量：**assists（动作次数）× assist ratio（相对成本系数）**，按 skill/实例/domain 下钻，entitlement 状态机 Compliant → Near capacity → Over-allocated；**AI 消耗按实例计量、不按租户拆分**——MSP 需自行二次加工（EMS 机会点）
  - BYOK：与 OEM 双轨；请求走客户云账号、第三方费用客户自付；模型别名映射、版本管理、区域 consent；监管市场隐藏外部供应商
  - 治理：AI Control Tower（资产清单/审批 playbook/风险合规/价值采纳）· Guardian 三道防护（Offensiveness / Prompt injection / Sensitive topic，各分 log-only / log+block 两档，16 安全分类）· AI Gateway 全局暂停/恢复 · 调用 LLM 前剥除 PII
  - Agent 工程：Base plan / Role / Instructions 三要素 · 单一用途工具 + 自然语言描述 · Interactive/Non-interactive 执行模式 · Execution Plans 全链路日志 · 版本控制 + 自动化 eval
- **互联网调研**（2026-08-21）：
  - SN Now Assist 2026：Foundation/Advanced/Prime 三档 SKU、assists 年度池、超量高价、70% 阈值告警、年度 reset（rollover 需协商）
  - Salesforce Agentforce：Flex Credits $500/10 万 credits（≈$0.005/credit）、per-user + consumption 混合、BYOM 可降本 30-50%
  - BYOK 行业实践：64% 企业 GenAI 买家已有直签 LLM 合同；BYOK 下平台收**软件费 + 平台费**（osFoundry 7.5% passthrough / OpenRouter 5% usage fee）；BYOK 仍需计量（功能门控、防滥用、价值分析）；密钥安全最低标准 = 信封加密 + KMS + JIT 解密 + 解密审计 + 序列化剥离 key 字段

## P4 · AI 审计与安全

### 决策：T5 审计深化为完整"AI 行为审计"，安全防护对标 SN Guardian 三道防护

**结论**：在 03 §P3 已定审计分层（L1 只保 T5b / L2-L3 完整审计链）基础上，补齐**日志详情、防护策略、密钥安全、保留期、数据驻留**五个方面，形成"每一次 AI 行为可解释、可导出、可防护"的安全闭环。

### T5 审计日志深化（对标 SN Execution Plans 全链路 + 审计台账）

**单条审计记录六要素**（每次调用最小记录单元 · P1 已定）：

| 要素 | 内容 | 档位差异 |
|:---|:---|:---|
| 身份 | 触发人（用户/系统/Agent）· 角色 · 租户 · 项目（PMS 关联） | 全部 |
| 行为 | 场景（M1-M6）· Agent · Skill · 档位（L1/L2/L3）· 动作类型（建议/起草/审批/执行/override） | 全部 |
| 模型 | 模型与版本 · 接入模式（托管/BYOK/本地）· 别名映射 | 全部 |
| 消耗 | credits · token 输入/输出 · 延迟 · 重试次数 | 全部 |
| 决策链 | **L2/L3 专属**：审批人 · 审批时间 · 审批动作（放行/驳回/编辑后放行）· override 原因 · 证据引用（CMDB 关联/历史案例） | L1 不记录 |
| 内容 | 输入（脱敏后）· 输出（脱敏后）· guardrail 命中（分类/动作 log/block） | L1 只存 hash，L2/L3 存原文（脱敏后） |

**审计页面能力**（ai-center 治理 Tab T5 增强）：
- 日志详情抽屉：单条展开六要素 + 输入/输出对比 + 审批链时间线 + 证据下钻
- 检索与筛选：触发人/审批人/场景/Agent/档位/时间/工单号/guardrail 分类
- 导出：CSV / PDF / JSON · **合规报告打包**（T1 审批 + T5 审计 + T6 override + T2 账单一次导出）
- **保留期配置**：默认 180 天，租户可配（90/180/365 天 · 对齐 tenant-management 已有 retention 字段），到期自动归档/删除留痕——满足 GDPR 数据最小化（07 §P2 CTE 测评点 5）

### 安全防护（对标 SN Guardian）

**三道防护，各分 log-only / log+block 两档**：

| 防护 | 覆盖范围 | 说明 | 对标 |
|:---|:---|:---|:---|
| **P1 · Prompt 注入检测** | 全平台所有 GenAI 调用 | 检测"忽略指令/越权/提示词劫持"类输入；block 时返回标准错误提示而非 AI 输出 | SN Guardian Prompt injection（全平台） |
| **P2 · 敏感内容过滤** | 对话类（Copilot/自助助手） | 16 安全分类（toxic/歧视/隐私侵犯/安全威胁/欺诈等）· 命中敏感主题重定向（转人工/建单）· 用户可"继续，不敏感"推翻（留痕） | SN 16 分类 O1-O16 + Fallback topic |
| **P3 · 输出白名单校验** | Agent 输出写入业务字段前 | AI 输出严格约束在预定义选项池内（ref-plan 前置共识 4 · MC8 Enum-Policy MCP 落地），非法值拦截并返回可选值 | EMS 特有（比 SN 更硬） |

**防护统计面板**：各防护 flag 总数/分类分布/按场景分布/防护延迟（guardrail 性能可度量——对标 SN Guardian Analytics）。

### PII 脱敏（对标 SN"调用 LLM 前剥除 PII"）

- **脱敏策略配置**（字段级）：姓名/手机/邮箱/IP/账号/身份证/银行卡 · 租户可增删字段与规则（正则）
- **执行位置**：LLM 调用前自动剥除，审计日志中的输入/输出均为脱敏后内容
- **命中统计**：每字段脱敏命中次数，审计可查"哪些数据差点出域"

### 异常检测（平台运营安全）

| 检测 | 规则 | 动作 |
|:---|:---|:---|
| 滥用检测 | 租户调用量突增 ≥10× 日均（防租户倒卖 AI 能力——BYOK 行业实践） | 告警平台运营 + MSP · 可临时限流 |
| 超时告警 | Agent 调用超时（M1 超时不阻塞主流程已定 · ref-plan 运行约束 4） | 回填空值 `ai-status=timeout` · 主流程继续 · 告警 |
| 异常模式 | 非工作时间批量调用 · 单用户异常高频 | 告警 + 审计标记 |
| 密钥安全 | key 解密审计（每次解密留痕）· 异常解密（非调用上下文） | 告警 + 密钥轮换建议 |

### 全局 AI 开关（对标 SN AI Gateway）

- **AI Gateway**：全局暂停/恢复 AI 交易（一键降级所有场景到 L1/停用）· 暂停期间所有 AI 入口返回"AI 服务暂停中"
- 与 T3 熔断（成本%/错误率%）互补：熔断是自动阈值，Gateway 是人工全局开关

## P5 · 内置 Agent 体系

### 决策：客户主层 = 8 个场景 Agent（运维任务命名）· 实现底座 = 7 个能力组件（ref-plan A1-A7）

**结论**（2026-08-21 用户拍板 · 替代 v1.0-v1.2 的"7 能力 Agent 为主层"设计）：Agent 库对外主层是 **8 个场景 Agent**——以运维任务命名（对齐 SN agentic workflow 命名方式：alert triage / impact analysis），客户与销售看到的是业务场景价值；ref-plan 的 7 个能力 Agent（A1-A7）降为**能力组件**（工程复用底座，解决"各产品不重复建 AI 服务"），在 Agent 编辑面的「实现」区块展示。

> **修订（2026-08-28 · 低代码产品线 AI 功能并入）**：低代码产品线 PM 权威文档《corteza-itsm-itam-fsm-ai-v1.md》将 ITSM/ITAM/FSM 的 16 项 AI 功能规划为 **7 个平台级通用 Agent（A1-A7）由 EMS 统一托管**。为对齐该口径，**A1-A7 升格为 Agent 库内的平台通用 Agent**（客户主层，取代本决策"不出现在 Agent 库主层"的呈现口径），承载低代码侧功能 + 作为 sa 系列场景 Agent 的复用底座（如 sa3 工单起草引用 A1/A3）。Agent 库从 8 个场景 Agent 调整为 **14 个**（ITOM 侧 7 个场景 Agent 保留 + A1-A7 升格进库，变更风险 sa4 / 服务请求 sa5 由 A4/A2/A6 承接、智能派工 sa8 并入 A7）。权威目录见 13 号文档 v2。

### 对外提供 · MCP 端点（客户外部 Agent 接入 · 2026-08-21 补）

**结论**：内置 MCP 可生成**对外端点**，把 EMS 数据能力提供给客户自己的外部 Agent（Claude Code / Codex / Cursor 等）——对标 SN MCP Server Console（把内部 skill 暴露为 MCP 工具）。场景：客户买了 EMS，内部团队用外部 Agent 做自己的自动化（查资产/拉工单/巡检），通过标准 MCP 协议直连 EMS 能力。

| 设计点 | 内容 |
|:---|:---|
| 端点形态 | 每个 MCP 生成独立 endpoint（如 `https://ems.example.com/mcp/cmdb-asset`）· 私有化部署用自有域名 |
| 凭证 | Token 签发 · 信封加密存储 · KMS 管理 · 解密审计（与 BYOK 密钥同标准）· 轮换即失效旧凭证 · 吊销端点 |
| 工具范围 | 默认仅只读工具（供外部查询）· 受控写入（建单/评论）需审批 |
| 权限与数据范围 | 绑定租户数据范围 + 平台角色（与平台内 RBAC 同源）· 可选自定义工具白名单 |
| 审计 | 外部调用进入审计（六要素）· 调用明细可导出 |
| 计费 | 纯数据 API 调用（无 LLM），订阅内含 · 异常突增触发防滥用告警 🔴 与商业化决策合并确认 |
| 接入指引 | 配置片段弹窗：Claude Code `claude mcp add` / Codex CLI / Cursor JSON 三种格式 |

**内置 MCP 目录语义（2026-08-21 用户指正）**：内置 MCP 为平台资产恒可用，目录表不显示"已启用"状态列（真正的启停控制 = Agent × MCP 白名单矩阵）；状态语义仅保留"自定义注册 · 待审批激活"一种例外。

> **筛选规则（2026-08-21 修订）**：① 模板必须满足"单一、可复用、模板化任务"；② **与场景 Agent 重名的功能不进 Skill 清单**（如"变更风险评估/派工推荐/资产健康巡检/CMDB 数据质量报告"由对应场景 Agent 承载，其内部的模板化子任务才可进 Skill）；③ 能力集功能是**业务条目**，其载体是场景 Agent（主）或 Skill/规则（辅），二者不可混为一谈。

**Skill 编辑面**：提示词模板 · 触发方式 · 枚举白名单（引用 M8）· 版本 · 启停 · 可见范围（全局/租户/项目）· 变更留痕。**Skill 与 Agent 的关系**：Skill 是可复用的单一任务能力（A 的能力原子），Agent 是绑定场景/模型/权限的调度体（对标 SN：skill = 单一任务 · agent = 编排载体）。**内置 Skill 不支持删除**（平台资产），只可停用；自定义 Skill 可删。

### 张力调和（3 项表面冲突的处理口径，销售/研发口径必须一致）

1. **"AI Agent Hub 编排引擎（A2A 多 Agent 协作）" vs 03 §P2"不做通用编排中枢"**：不冲突。03 否定的是**与场景无关的通用编排引擎**（L4 无人值守路线）；能力集的"编排"= **场景白名单内的多 Agent 串并行组合**（M1-M6 场景工作流，如 M2 RCA = A2 检索 + A1 解析）。A2A 协作框架的落地形态就是"场景 → Agent 组合"映射表（P5）。对外话术：**"场景化多 Agent 协作"**，不说"通用编排中枢"。
2. **"Agent 信任度模型（置信度自动调节自主权）" vs 03 §P3"不用 LLM 自报置信度作为闸门"**：不冲突。信任度 = **历史执行准确率统计**（MC8 Feedback-Learning 成对存档 + MC9 的命中率数据）驱动档位建议；自主权调节（建议→审批后执行→全自动 = L1/L2/L3 切换）必须叠加 T1 审批（新增 L3 场景走审批卡点）。**单次调用的 LLM 置信度永远不作为自动执行闸门**（03 硬约束，对销售解释为"平台用长期准确率而非单次置信度控制自主权，更稳更合规"）。
3. **"AI Token 用量与预算管理" vs "AI Credits 计费"**：能力集的 Token 用量管理被**完整包含**在双口径设计中——成本口径就是 Token 监控（按模型/产品/租户维度 + 预算预警 + 成本分摊），收费口径（credits）是 MSP 多租户计费的实现升级。对客户话术可继续说"Token 用量透明可控"，产品实际提供双视图。
