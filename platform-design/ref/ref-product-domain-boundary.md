# EMS 统一平台 — 域间关系与数据流转说明

> 版本：v1.0 | 更新日期：2026-05-15
> 参考来源：EMS 架构全景图、ITIL v4、ServiceNow / BMC / SolarWinds 行业实践

---

## 一、系统定位总览

| 域 | 全称 | 核心职责 | 本质 |
|:---|:---|:---|:---|
| **EMS** | Enterprise Management System | 统一 SaaS 平台入口 — 认证/授权/租户/AI 编排/千人千面大屏 | 编排层（不自研子域 AI） |
| **ITOM** | IT Operations Management | 基础设施全栈监控 — 设备监控/网络拓扑/告警引擎/自动发现/NCM/IPAM | 被动采集 + 设备性能监控 |
| **NPM** | Network Performance Management | 网络质量管理 — 云拨测/延迟/丢包/抖动/Traceroute/应用可用性 | 主动探测 + 网络质量监控 |
| **CMDB** | Configuration Management Database | 共享数据层 — CI 资产/关系图谱/服务映射/影响面计算/变更审计 | 所有域的知识图谱底座 |
| **ITSM** | IT Service Management | IT 服务管理 — 事件/变更/问题/服务请求/知识库 | 流程管理 + 合规通道 |
| **FSM** | Field Service Management | 现场服务管理 — 智能派工/现场执行/备件/SLA 追踪 | 最后一公里执行闭环 |

**核心原则**：

- ITOM 与 NPM 本质都是**监控系统**（一个被动采集设备性能，一个主动探测网络质量），两者对 CMDB 的写入模式一致
- CMDB 是**横切所有业务域的共享数据层**，自身具备**数据治理类 AI**（自动分类、关系补全、异常检测），同时为所有跨域 AI 提供知识底座
- ITSM 变更管理是 CMDB 属性更新的**合规通道**
- EMS 是**编排层**，通过 AI Agent Hub + MCP 协议横向调用所有子域

## 二、域间角色分类

```
┌─────────────────────────────────────────────────┐
│           EMS 统一平台（编排 + AI 入口）           │
└───────────────────────┬─────────────────────────┘
                        │ MCP 协议调用
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
┌──────────────┐  ┌──────────┐  ┌──────────────┐
│  生产者 (写入)  │  │ 数据枢纽  │  │  消费者 (读取)  │
│  ITOM + NPM   │→│   CMDB   │→│  ITSM + FSM  │
└──────────────┘  └──────────┘  └──────────────┘
```

| 角色 | 域 | 说明 |
|:---|:---|:---|
| **数据生产者** | ITOM、NPM | Discovery 写入 CI 资产、拓扑关系、路径质量 |
| **数据枢纽** | CMDB | 存储所有 CI 及其关系，供全域查询 |
| **数据消费者** | ITSM、FSM | 读取 CMDB 做影响分析、CI 位置查询、变更评估 |
| **编排层** | EMS | 不直接存储业务数据，通过 MCP 横向调用各域 |

## 三、域间数据流详解

### 3.1 写入 CMDB（数据流入方向：↓）

| 源域 | → CMDB | 强度 | 写入内容 | 行业依据 |
|:---|:---|:---|:---|:---|
| **ITOM** | → CMDB | **强写入**（最大来源） | CI 资产（设备/VM/软件）、L2/L3 拓扑关系、设备发现结果 | ServiceNow Discovery / Service Mapping |
| **NPM** | → CMDB | **写入** | 网络路径拓扑、链路质量评分、Traceroute 路径关系、端到端延迟基线 | Service Graph Connector（NPM ≈ 网络层 Discovery） |
| **ITSM** | → CMDB | **写入**（合规通道） | 变更实施后 CI 属性更新、事件状态标记(degraded)、已知错误标记 | ITIL v4 Change Management post-implementation |
| **FSM** | → CMDB | 弱写入 | 工单闭环 → CI 状态回写（如硬件更换后序列号/状态变更），通过 workflow 驱动 | ServiceNow FSM → Change Record → CMDB |

### 3.2 读取 CMDB（数据流出方向：↑）

| CMDB → | 目标域 | 强度 | 提供内容 | 用途 |
|:---|:---|:---|:---|:---|
| CMDB | → **ITOM** | 读取 | CI 上下文（影响面、服务链路） | 告警富化、根因分析上下文 |
| CMDB | → **NPM** | 弱读取 | 服务路径依赖 | 探测优先级建议："哪些链路承载关键业务？" |
| CMDB | → **ITSM** | **强读取** | 影响分析（变更影响面、CI 依赖链、服务映射） | ITIL v4 Change Impact Analysis |
| CMDB | → **FSM** | 读取 | CI 位置/配置/历史事件 | 派工上下文（去哪里、修什么、历史问题） |

### 3.3 跨域横向流转（不经过 CMDB）

| 源域 | → 目标域 | 触发条件 | 流转内容 | 说明 |
|:---|:---|:---|:---|:---|
| **ITOM** | → **ITSM** | 告警自动升级 | 创建 Incident 事件工单 | ITIL Alert-to-Incident 流程 |
| **ITSM** | → **FSM** | 事件/变更需现场处理 | 派工工单 | Dispatch workflow |

> **重要说明**：NPM 与 ITOM 是完全独立的产品，NPM 不向 ITOM 上报数据。两者通过各自 MCP Server 向 EMS Agent Hub 提供数据，EMS 在编排层做跨产品关联分析。

## 四、端到端事件流转全链路

```
ITOM 检测到设备异常 / NPM 检测到链路异常（各自独立）
    │
    ▼ EMS Agent Hub 跨域编排
EMS 并行查询 ITOM 告警 + NPM 质量数据 + CMDB 拓扑
    │
    ├─ AI 告警降噪（合并重复/低优告警）
    ├─ AI 根因分析（结合 CMDB 拓扑定位根因）
    │
    ▼ 告警升级为事件
ITSM 创建 Incident
    │
    ├─ AI 知识推荐（RAG 检索历史方案）
    ├─ AI 变更风险评估（结合 CMDB 影响面）
    │
    ▼ 需要现场处理时
FSM 智能派工
    │
    ├─ 技能/位置/负载匹配最优工程师
    ├─ 现场执行 + SOP 指引
    │
    ▼ 工单闭环
FSM → CMDB（CI 状态回写）
FSM → ITSM（工单关闭确认）
```

**关键要点**：
- NPM 和 ITOM 是**独立产品**，各自监控不同域（NPM 监控网络质量，ITOM 监控设备/服务）
- EMS Agent Hub 负责**跨产品编排**：同时查询多个独立产品的数据，联合分析
- 每个节点都**读取 CMDB** 获取上下文（影响面、CI 位置、服务映射）
- 每个节点的**处理结果写回 CMDB**（状态变更、新关系、事件记录）

## 五、EMS AI Agent Hub — MCP 调用关系

EMS 作为编排层，通过 MCP（Model Context Protocol）标准化调用各子域：

| EMS AI Agent | 调用目标域 | 方向 | MCP 工具 | 用途 |
|:---|:---|:---|:---|:---|
| 🔇 告警降噪 | ITOM | 读取 | `alert_query` | 获取告警流进行聚合分析 |
| 🔍 根因分析 | ITOM | 读取 | `alert_query` / `metric_fetch` | 获取告警 + 时序指标 |
| 🔍 根因分析 | CMDB | 读取 | `cmdb_topology` | 获取 CI 关系图做影响面分析 |
| 📈 容量预测 | NPM | 读取 | `npm_probe` | 获取拨测质量趋势 |
| 🔗 事件关联 | ITSM | 写入 | `incident_create` | 创建事件工单 |
| ⚠️ 变更风险 | CMDB | 读取 | `cmdb_topology` | 影响范围评估 |
| ⚠️ 变更风险 | ITSM | 读取 | `change_calendar` | 查询变更窗口/冲突检测 |
| 🔍 根因/变更 | ITSM | 读取 | `knowledge_search` | 查询知识库/历史案例 |
| 👷 智能派工 | FSM | 读取+写入 | `dispatch_opt` | 查询工程师信息 + 创建派工 |
| ⚙️ 配置管理 | ITOM | 读取 | `config_backup` | 获取设备配置备份 |

**设计原则**：EMS Agent Hub **不替子产品重复实现 AI 算法**，而是：
1. 各子产品自研领域 AI（ITOM 做降噪/根因，ITSM 做知识推荐，FSM 做派工）
2. EMS 通过 MCP 调用各子产品已有能力，进行**跨产品联合推理**和**端到端编排**

## 八、CMDB 自身的 AI 能力（数据治理类）

> CMDB 并非"不做 AI"。CMDB 拥有聚焦于**数据治理**领域的 AI 能力，目标是保证数据本身的准确性和完整性。
> 与 ITOM/ITSM/FSM 的"业务决策型 AI"（降噪/根因/派工）不同，CMDB AI 的职责是"让数据更好"。

| CMDB AI 能力 | 说明 | 对应原型页面 |
|:---|:---|:---|
| **AI 自动分类** | 新发现设备自动识别类型（网络设备/服务器/云实例），准确率 98%+ | `cmdb-discovery.html` |
| **AI 关系补全建议** | 基于拓扑分析，发现缺失的 CI 关系并推荐补全 | `cmdb-ci-list.html` |
| **AI 发现策略推荐** | 分析未纳管子网，推荐新增发现规则以扩大覆盖 | `cmdb-discovery.html` |
| **AI 异常检测** | 检测发现结果中的异常设备或意外变更 | `cmdb-discovery-detail.html` |
| **AI 影响面分析** | 给定 CI 变更，自动分析上下游影响范围（服务/业务/用户群） | `cmdb-portal.html` |
| **AI 数据质量报告** | 生成 CMDB 健康度报告，定位数据质量问题 | `cmdb-data-quality.html` |
| **AI CI 类型建议** | 基于当前环境推荐新的 CI 类型定义 | `cmdb-settings.html` |

**CMDB AI vs 其他域 AI 的区别**：

| 维度 | CMDB AI（数据治理型） | ITOM/ITSM/FSM AI（业务决策型） |
|:---|:---|:---|
| 目标 | 让数据更准确、更完整 | 基于数据做运维决策 |
| 输入 | CMDB 自身数据（CI、关系、发现结果） | 跨域数据（告警+指标+拓扑+工单） |
| 输出 | 分类标签、补全建议、质量报告 | 根因定位、风险评分、派工方案 |
| 依赖 | 仅依赖 CMDB 内部数据 | 需要 CMDB + 其他域数据组合 |

## 九、关键设计约束

1. **CMDB 数据质量是 AI 的天花板**
   CMDB 数据准确率 < 60% 时，所有依赖 CI 上下文的 AI 功能（根因分析、影响面、变更风险）基本不可用。

2. **ITOM Discovery 是 CMDB 数据的最大来源**
   没有 ITOM 的自动发现，CMDB 就是空壳。Discovery 的覆盖率直接决定 CMDB 数据的完整性。

3. **ITSM 是 CMDB 变更的合规通道**
   CI 属性变更不应绕过 ITSM 直接写入（除 Discovery 自动化场景），确保变更可审计、可回溯。

4. **NPM 与 ITOM 是独立产品，不存在数据上报关系**
   NPM 和 ITOM 分别监控不同域（网络质量 vs 设备/服务），各自通过 MCP Server 向 EMS Agent Hub 提供数据。跨产品关联分析由 EMS 编排层完成。

5. **FSM 闭环是数据链路的终点**
   现场维修完成后，FSM 通过 workflow 将结果（新序列号、状态变更）回写 CMDB，形成完整数据闭环。

## 十一、EMS 平台三层架构 — Portal 与各产品的治理关系

> 前文（一～十）聚焦于 **产品与产品之间的数据流**（ITOM↔CMDB↔ITSM↔FSM↔NPM）。
> 本节补充 **EMS Portal 平台层对各产品的管控流与数据聚合流**。

### 11.1 三层架构定位

```
┌─────────────────────────────────────────────────────────────────┐
│              ① EMS Portal 层 (统一体验入口)                       │
│     SSO · 多租户隔离 · License/SKU · 统一导航 · AI 对话入口       │
└────────────────────────────┬────────────────────────────────────┘
                             │ 平台治理（认证/授权/模块启停）
┌────────────────────────────┼────────────────────────────────────┐
│              ② AI 智能层 (Agent Hub)                              │
│     Agent 编排 · MCP 协议 · RAG 知识引擎 · LLM Gateway           │
└────────────────────────────┬────────────────────────────────────┘
                             │ MCP 标准化调用
┌────────────────────────────┼────────────────────────────────────┐
│              ③ 产品层 (各子产品 MCP Server)                        │
│     ITOM · CMDB · ITSM · FSM · ITAM · NPM                       │
└─────────────────────────────────────────────────────────────────┘
```

| 层级 | 核心职责 | 对应原型目录 |
|:---|:---|:---|
| **Portal 层** | 统一身份认证、租户隔离、产品授权、导航聚合、AI 对话窗口 | `portal/` · `org/` · `settings/` |
| **AI 智能层** | Agent 注册/发现/编排、跨产品联合推理、知识检索 | `ai/` |
| **产品层** | 各域自研业务逻辑 + 暴露 MCP Server 接口 | `itom/` · `cmdb/` · `itsm/` · `fsm/` |

### 11.2 Portal 平台级服务 → 各产品治理关系

Portal 不仅通过 AI Hub 间接调用产品，还直接承担以下平台级治理职责：

| EMS Portal 能力 | 治理方向 | 对各产品的影响 | 对应原型 |
|:---|:---|:---|:---|
| **统一认证 (SSO)** | Portal → 所有产品 | 提供身份认证、会话管理、Token 签发；产品层不自建登录 | `org/org-structure.html` |
| **多租户隔离** | Portal → 所有产品 | 控制各产品的租户数据隔离边界，租户 CRUD 统一在 Portal 完成 | `org/tenant-management.html` |
| **License/SKU 管理** | Portal → 所有产品 | 控制各产品模块的启停和功能授权（如：未购 NPM 则隐藏拨测入口） | `org/license-management.html` |
| **产品管理** | Portal → 所有产品 | 产品模块启停、SKU 绑定、功能开关 | `org/product-management.html` |
| **统一导航** | Portal → 所有产品 | 聚合所有产品页面至统一侧边栏，提供跨产品一键跳转 | 全局侧边栏 |
| **RBAC 角色权限** | Portal → 所有产品 | 统一角色/权限模型，各产品消费 Portal 下发的权限规则 | `org/role-management.html` |
| **数据同步管理** | Portal → 产品间 | 管理各域间数据同步任务（频率/范围/冲突策略） | `settings/sync-management.html` |
| **第三方对接** | Portal → 外部系统 | 统一管理外部系统集成（邮件/短信/Webhook/LDAP/RADIUS） | `settings/third-party.html` |

**关键设计约束**：

- 产品层**不自建认证**——所有认证请求由 Portal SSO 统一处理
- 产品层**不自建租户模型**——租户边界由 Portal 下发，产品层只做数据过滤
- License 控制的是**功能入口可见性**，不影响已存储的历史数据

### 11.3 Portal Dashboard — 跨产品数据聚合

原型 `portal/dashboard.html` 展示了 Portal 直接从各产品聚合运维态势数据：

```
EMS Portal Dashboard（运维门户）
  │
  ├── 从 ITOM 聚合：告警总数 · 降噪统计 · 设备健康度 · 在线率
  ├── 从 CMDB 聚合：CI 总数 · 数据质量评分 · 关系覆盖度 · 未纳管设备数
  ├── 从 ITSM 聚合：待处理工单数 · SLA 合规率 · 平均解决时长 · 积压工单
  ├── 从 FSM 聚合：派工中任务数 · 完成率 · 工程师利用率 · SLA 履约率
  ├── 从 NPM 聚合：链路可用率 · 延迟基线 · 异常探测数 · 拨测成功率
  │
  └── AI 摘要：跨产品运维态势自然语言摘要（由 Agent Hub 生成）
```

**聚合模式**：Portal Dashboard 通过各产品 **只读 API / MCP Resource** 获取聚合指标，不直接查询产品数据库。

### 11.4 平台治理流 vs 业务数据流 对比

| 维度 | 平台治理流（Portal → 产品） | 业务数据流（产品 ↔ 产品） |
|:---|:---|:---|
| **发起方** | EMS Portal | ITOM / NPM / ITSM / FSM |
| **内容** | 身份令牌、租户 ID、权限规则、License 配置 | CI 数据、告警事件、工单、派工请求 |
| **方向** | 单向下发（Portal → 产品） | 双向流转（如 ITOM ↔ CMDB） |
| **频率** | 低频（配置变更时触发） | 高频（实时/准实时数据流） |
| **失败影响** | 产品不可用（无法认证/无权限） | 业务功能降级（数据不完整） |

## 十二、ITAM 域 — 资产生命周期管理

> EMS 平台架构中 **ITAM** 为独立产品域，与 CMDB 并列。

### 12.1 ITAM 与 CMDB 的关系

| 维度 | CMDB（配置管理） | ITAM（资产管理） |
|:---|:---|:---|
| **关注点** | CI 之间的拓扑关系、服务依赖、影响面 | 资产的采购/折旧/合同/成本/报废 |
| **核心实体** | CI（Configuration Item） | Asset（与 CI 一一映射或一对多） |
| **数据视角** | 技术视角（运行状态、连接关系） | 财务视角（成本、折旧、合同到期） |
| **共享数据** | CI 基本属性（名称/类型/序列号/位置） | 同一 CI 的财务属性（采购价/供应商/合同） |
| **写入来源** | ITOM Discovery + NPM 路径发现 | 采购系统导入 + 手工录入 + 盘点 |

### 12.2 ITAM 数据流

| 交互方向 | 描述 | 触发场景 |
|:---|:---|:---|
| **ITAM ← CMDB** | 读取 CI 基本属性（设备类型/位置/在线状态） | 资产台账关联技术状态 |
| **ITAM → CMDB** | 写入资产状态变更（报废 → CI 下线标记） | 资产报废/退役流程 |
| **ITAM → ITSM** | 合同到期预警 → 触发变更请求（续约/替换） | 合同到期前 N 天自动触发 |
| **ITAM ← ITSM** | 变更完成后回写（硬件替换 → 资产台账更新） | 变更工单闭环 |
| **ITAM ← FSM** | 现场盘点结果回写（实际序列号/位置校正） | 现场盘点任务闭环 |

### 12.3 ITAM 在总架构中的位置

```
         EMS Portal
              │
         AI Agent Hub
              │ MCP
    ┌─────────┼─────────┬──────────┬──────────┬──────────┐
    │         │         │          │          │          │
  ITOM      CMDB      ITSM       FSM       ITAM       NPM
    │         │                              │
    │    CI 基本属性 ◄───────────────────► 资产属性
    │    (技术视角)                      (财务视角)
    │         │
    └── Discovery ──► CI 写入
```

**ITAM 暂未在本版原型中包含页面**，但架构设计已预留产品位，后续迭代时补充 `itam/` 目录。

**三类数据流总结**：

| 流类型 | 方向 | 内容 | 本文覆盖章节 |
